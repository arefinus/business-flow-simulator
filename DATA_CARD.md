# Data card

## Summary

This repository ships **no external data**. Every input is generated by a seeded
synthetic workload generator (`src/business_flow_simulator/workload.py`) from a scenario
file in `configs/scenarios/`. The one committed data file,
`examples/fixtures/v1/workload_baseline.json`, is the materialised baseline workload at
seed 42 and is labelled in `examples/fixtures/v1/FIXTURE.md`.

| Field | Value |
|---|---|
| Provider | none (authored synthetic generator in this repository) |
| Terms | MIT, same as the code |
| Evidence label | `demo` for every number produced from it |
| Record unit | one purchase order, with 1 to 4 order lines, placed by a fictional customer account |
| Target | none; this is a simulation input, not a supervised dataset |
| Collection | not applicable; generated |
| Personal data | none; there are no people in the model |
| Company data | none; organisation names are fictional ("Northwind Demo Supply", "Blue Harbor Demo Retail") |

## Columns (workload file)

Top level: `schema_version`, `label` (always `synthetic`), `scenario_id`, `seed`, `skus`,
`initial_stock`, `reorder_point`, `reorder_qty`, `customers`, `opening_balances_cents`,
`orders`. Each order: `order_id` (`SYN-PO-nnnnnn`), `customer_id` (`SYN-CUST-nn`),
`t_arrival` (simulated minutes), `lines[]` (`sku`, `qty`, `unit_price_cents`) and a
`faults` block fixing every fault draw for that order (`shipment_delay_minutes`,
`duplicate_invoice`, `replay_same_id`, `payment_failures`, `price_variance_bps`,
`cancel_after_minutes`, where `-1` means no cancellation). Full schema:
`schemas/workload.schema.json`; narrative in `docs/schema.md`.

## Generation process

1. A scenario YAML fixes the seed, horizon, workload ranges, fault probabilities and the
   retry policy (`schemas/scenario.schema.json`).
2. `generate_workload` draws SKU prices, customer assignment, exponential inter-arrival
   gaps, line counts and quantities, then every fault outcome, from one
   `random.Random(seed)`. Arrivals are clipped to 60% of the horizon so orders have time
   to finish.
3. The result is frozen. The three policies are then run on the identical workload, so
   any difference between policies is due to the policy alone.

## Splits and missingness

There are no train/validation/test splits and no missing values: nothing is learned from
the data. The simulator is a deterministic function of (scenario, workload, policy,
assumptions).

## Cost and service-time assumptions

`configs/assumptions.yaml` declares every service time (minutes) and cost (integer cents,
fictional USD). They are inputs, not measurements of any organisation, and they are
documented as such in `docs/method.md`.

## What a real deployment would need

To run on real operational data you would write an adapter that emits `Event` records
conforming to `schemas/event.schema.json` from your own order, receipt, invoice and
payment tables. That adapter is not part of this repository and no real-data run has
been performed here.
